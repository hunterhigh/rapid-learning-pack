# Package architecture and interaction

Use this reference when turning a researched domain into a navigable learning artifact.

## Information layers

Expose the package in layers without hiding any layer:

1. **Orientation:** domain boundary, map, full index, tier legend, and the fast route.
2. **Fast path:** a coherent sequence containing the highest-value 50–60% for the user's stated rapid-learning window.
3. **Extended knowledge:** broader cases, nuance, alternative models, and less frequent but still useful topics.
4. **Reference layer:** glossaries, detailed specifications, vendor-specific material, source ledger, and lookup tables.

The fast path is a route through the package, not a separate abbreviated package. A direct link or index must make every module immediately accessible.

## Module design

Choose only the elements that improve the topic. A strong module commonly provides:

- a direct answer or governing idea;
- a diagram when the concept is structural, sequential, relational, or stateful;
- the underlying mechanism and causal chain;
- why the concept matters in real work;
- boundaries, tradeoffs, and common failure modes;
- one or more worked cases;
- questions or checks usable in real decisions;
- sources and optional deeper branches.

Worked cases occur inside the material. Do not convert them into assignments unless the user asks.

## Priority presentation

Make priority visible at the index and module levels. Explain priority using usefulness, transfer, dependency, frequency, error cost, and durability—not difficulty or assumptions about the learner.

Avoid labels such as “beginner content” when the actual distinction is foundational, high-frequency, or prerequisite knowledge. A foundational topic can be technically deep and high value.

## Interaction contract

Accept ordinary questions without requiring commands or templates. Useful question modes include definition, mechanism, comparison, failure analysis, application, evidence, and deeper detail, but the user need not name the mode.

Default response shape:

1. answer the question directly;
2. explain the mechanism or reason;
3. connect it to a representative work situation;
4. state important boundaries or disagreement;
5. provide evidence or navigation to related material when useful.

Let the user request shorter or deeper answers at any time. Do not withhold detailed information because a simpler explanation might suffice.

## Language and visuals

- Use plain language while retaining exact domain terminology.
- Define a term at first use, then use it normally.
- Use analogies as entry points and return to the real mechanism before concluding.
- Prefer short sections and progressive disclosure over an arbitrary total word limit.
- Use flow diagrams for sequences, system maps for components, state diagrams for transitions, relationship diagrams for data models, wireframes for interface structure, and tables for exact comparisons.
- Avoid decorative icons or illustrations that do not reduce search or comprehension cost.

## Optional adaptation

The package may remember topics the user has asked about, preferred response depth, or recurring work contexts when that improves navigation. Do not infer mastery, restrict access, grade progress, or introduce tests from those observations. User corrections override any inferred preference.
